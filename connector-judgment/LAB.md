# Judgment: remember decisions and confirm lessons

## Requirements and finish line

Continue your existing Hive Mind Sheet, Google connection and registered working Doc. GPT Work coordinates the downstream workflows; Apps Script continues transcript ingestion and task merging. Sheets remembers state, and one Judgment Log Doc makes decisions and lessons readable.

- Preserve Tasks A–P, Reviews, Drafts, accepted sources, historical results and stable IDs.
- Use one designated manual writer and name the human who may confirm rules on your board. You can be that human from initial setup.
- Let a new authorized workflow propose a useful lesson automatically, with its reason and evidence.
- Keep proposed lessons inactive until you explicitly confirm exact wording, version and scope.
- Verify that a fresh Work conversation finds an applicable confirmed rule and excludes it from unrelated work.
- Keep source facts, document approval and business-task completion separate from learning.

**Finish line:** one useful proposal, one explicit human confirmation, a verified active rule in your existing board and Log, and correct read-only discovery by Executor, Enforcer and Feedback. No document approval, sending or business-task completion follows from confirming a rule.

The reference account demonstrated this narrow manual path. Your own Google access, write capability and author binding still need to be checked. You do not need a new Sheet, an upfront code packet or a deliberately interrupted live run.

## 1. Inspect your board and choose the method

Start in a new Work conversation. If your workspace provides the worked implementation, type `@`, select **NMSU Hive Mind** under Plugins, and describe the task. Executor, Enforcer, Feedback and Judgment are skills inside that one plugin; selecting four separate plugins is unnecessary.

The reference package is NMSU Hive Mind 1.3.0, containing Executor 1.4, Enforcer 2.1, Feedback 1.1 and Judgment 1.0. Ask Work to verify the relevant installed methods and supporting references. The plugin supplies instructions; your existing Google connection supplies access to Docs and Sheets. Confirm the intended Google account when multiple connections are available.

If you are building your own method, use these requirements and observable checks. The worked plugin is a reference implementation, not an upfront code requirement.

Ask for an inspection and setup proposal:

> Inspect my existing Hive Mind board [BOARD], registered working Doc and approved Learning destination. Propose Judgment setup using one readable Log Doc and compatible hidden storage in this same Sheet. Name the designated human, writer, three scopes, accepted evidence and exact write ownership. Show concrete setup records and disposable test targets before enabling them. Preserve historical work. Use existing Google tools; identify a concrete capability gap before proposing a helper. Do not write yet.

**Check:** Work identifies your actual board and Doc, existing outputs and unfinished effects. It distinguishes accessible files from accepted evidence. It proposes no task-column changes, competing folder or new downstream Apps Script workflow.

## 2. Register the Log, authority and scopes

Review and authorize the concrete setup. Keep one registered Judgment Log for the board in your approved Learning destination. Save its actual Doc ID and the designated human's authority in Sheets. Installation alone does not enable requests or transfer writer ownership.

The Log presents readable entries and history. Hidden Sheet records retain exact versions, source references, confirmation, intent, known IDs and completion. Both must agree before affected work proceeds.

Every entry needs an explicit scope:

| Scope | Example | Where it applies |
| --- | --- | --- |
| This task/document | Preserve the inclusive duration wording in this agenda. | Only the named task and, when specified, the exact Doc. |
| This task type on this board | Demo agendas should state whether questions fit within total duration. | Matching demo-agenda work on this board. |
| All tasks on this board | Distinguish task deadlines from event dates. | Relevant work across this board's task types. |

Project and audience conditions may narrow each scope. Work should recommend the narrowest useful scope. A task/document rule does not automatically become a task-type rule. A board-wide rule does not automatically apply to another participant's board.

Confirm any task-type mapping explicitly. Similar titles are insufficient. A copied board needs its own authority and deliberate adoption of any rules.

**Check:** Your own designated human can confirm lessons immediately. The setup names one writer and preserves all earlier source approvals, requests and results.

## 3. Produce one useful lesson automatically

Use a new authorized disposable item on your existing board. Historical test Docs and completed requests remain evidence, not writable fixtures. If setup creates a test Doc, label its origin and register it separately; normal operation continues the same working Doc.

For a Feedback example, choose a short paragraph and ask for a small change already supported by an accepted source. If the source states that a 20-minute session includes questions, select a sentence such as “Duration: 20 minutes.” and comment:

> Please clarify that questions are included.

Leave the sentence unchanged yourself. Tell Work that you personally added the comment. Work must discover its real thread/post IDs and save the exact author/content/version binding before enabling the request. A matching display name or account indicator alone does not establish human authorship.

Run the enabled item:

> Use the installed Hive Mind methods. Board: [BOARD]. Request: [REQUEST], version [VERSION]. Reconstruct the enabled request, registered Doc, accepted sources, human authority and Judgment context from durable records. Complete the authorized primary work in the same Doc and original thread. Automatically consider one useful lesson, check existing entries and propose its narrowest useful scope with a reason and evidence. Save any proposal separately as Proposed before final parent completion. Do not activate a rule, approve the Doc, complete the business task or schedule anything. Stop on uncertainty. If already complete, return the saved result without repeating effects.

A lesson is useful when it can prevent a recurring mistake or preserve an explicit standard. Routine edits, missing facts and duplicate preferences may produce no new lesson. An Enforcer finding can support a proposal, but a machine finding never confirms a rule.

**Check:** The requested primary change and response are verified once. Any lesson remains Proposed and has no authority. Its evidence distinguishes human direction, accepted facts and machine observations. Work may finish primary work while a saved lesson awaits confirmation.

## 4. Confirm exact wording, version and scope

Review the proposed wording, scope, reason and example together. Ask for a revision or narrower scope if needed. Changed wording or scope creates a new proposed version; it does not inherit confirmation.

When satisfied, use the actual entry ID and version shown by Work:

> Confirm [LESSON ID] version [VERSION]

Work should save your explicit action against the displayed wording and scope, update the same Log with a revision guard, verify native readback and save the final activation commit. A typed Confirmed label alone is insufficient. “Looks good,” approving a document, resolving a comment and accepting a suggestion do not confirm a lesson.

**Check:** Exact wording and scope remain intact; the designated human and original confirmation evidence are recorded; the Log and final Sheet activation agree. Proposed and confirmed entries are distinguishable, and summaries show the current state. Stale headings or empty-state messages need presentation maintenance, not another rule confirmation or a change to the rule.

Confirmed rules must respect accepted facts and higher-priority instructions. Conflicts require a recorded human resolution. Rules can be rejected, superseded or retired while preserving history. Do not broaden or retire a rule merely to fill an acceptance table.

## 5. Prove fresh-context discovery

Start a genuinely new Work conversation with Hive Mind selected. Supply your board and task/Doc context, without earlier conclusions or local evidence files:

> Read-only Judgment discovery. Board: [BOARD]. Load the installed Executor, Enforcer, Feedback and Judgment methods and required references. Reconstruct active decisions/rules and human authority directly from Sheets, the registered Log and current evidence. For each consumer, report applicability to (1) the matching task and registered Doc, (2) that task with a different Doc, and (3) an unrelated task/Doc. Show selected or excluded versions, reasons, scope restrictions and confirmation/activation IDs. Preserve completed requests. Perform zero edits, replies, proposals, ledger writes or workflow executions.

Expected interpretation depends on the scope you actually confirmed. For a task-and-document rule, the matching context selects it; the same task with another Doc and unrelated work exclude it. A task-type or board-wide rule has different matching conditions. All restrictions must match; do not assume the example's answers apply to every rule.

- Executor uses applicable rules when planning a future authorized draft.
- Enforcer independently checks the draft against applicable confirmed rules and accepted originals.
- Feedback considers them when interpreting a future authorized comment.

Discovery grants no permission to run those workflows. A completed historical request stays complete. Save the distinction between a reported fresh Work result, independent connected readback and your own account's checks. Read-only discovery does not prove that a new generation or publication followed the rule.

**Check:** Work reconstructs the rule and authority without earlier chat history, selects/excludes it for the right reasons, and performs no writes. The original Doc, reply and completed records remain unchanged.

## 6. Handle decisions and interruptions clearly

A document/task decision records what a human chose and why. A proposed lesson asks whether that choice should generalize. Keep them separate. If a source already supplies a fact, Work should preserve that fact rather than treating it as a discretionary choice. Missing facts need clarification or source acceptance, not invented rules.

Not every edit needs another Enforcer review. Ordinary supported wording, formatting and clarification usually do not. Commitments, scope, safety, disclosures, previous findings and substantial uncertainty require a recorded review decision bound to the affected document state.

If a save stops, retain the request, operation and known Doc/thread/reply IDs. Ask Work to inspect current state against the saved intent before continuing. Do not rename the request, repost the comment, regenerate the lesson or make another draft to force a retry.

For an exact-formatting mismatch, preserve the frozen expectation and actual result. A human may authorize a precisely bounded repair or acceptance of the observed differences, with linked evidence. Fluent wording or a mostly correct result is not exact verification. Do not weaken comparisons silently.

The reference test encountered two paragraph-ending newline style differences after linking evidence. A human explicitly authorized record-only reconciliation; Work preserved the original failed verification, committed the existing proposal and finished only the missing records. Participants need not repeat this failure. Your exercise can finish without deliberate live fault injection.

Manual single-writer operation reduces conflicts but is not atomic locking. Broader structures, task-type/board-wide activation, revision/conflict/retirement cases, participant replication and unattended operation need evidence appropriate to their risks. They are not certified by the narrow reference demonstration.
