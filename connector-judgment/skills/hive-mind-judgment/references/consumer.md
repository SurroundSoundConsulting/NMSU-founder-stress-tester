# Consult Judgment during authorized work

Used by Executor method 1.4, Enforcer 2.1 and Feedback 1.1. The installed Judgment skill and this reference must be readable. If packaged relative references cannot be loaded, explicitly load hive-mind-judgment and its consumer/records references by skill name; unavailable content stops new dependent work. Keep one maintained copy of this procedure in the combined plugin.

## Before planning or acting

1. Run the role's normal existing-work check. A completed historical request returns its original result read-only, with no learning append. A method update does not reopen it. Inspect uncertain previous effects before new work.
2. Read this board's enabled Judgment configuration and exact human designation. Use one registered Log and compatible hidden ledger. A copied board needs its own adoption/authority; do not use another board's grants. New methods require deliberately authorized configuration/request mapping. Preserve historical methods and their source contracts.
3. Reconstruct all relevant entries, actions, complete manifests, intents and commits. Resolve by IDs after sorting. Read the current Log, accepted originals and relevant human comments. Inspect tabs, suggestions and native structure; a Log with opaque/pending-suggestion content needs reconciliation, not flattened interpretation.
4. Select task/document, task-type and board entries with their project/audience restrictions. Use the human-confirmed task-type mapping. Record exclusions. Proposed lessons, rejected/retired/superseded versions and unrelated entries do not govern work. A relevant unresolved decision or uncertain Judgment write blocks affected work.
5. Assess current evidence, accepted facts, higher-priority instructions and all overlapping applicable decisions/rules. Record actual passages and reasons, including the strongest relevant contradiction. Source freshness/quote presence is not entailment. Confirmed rules cannot override facts or permissions. Conflicts need explicit human resolution, not latest-timestamp precedence. Machine assertions that checks passed are not independent review.
6. Save a `judgment_application` companion before the role's effect intent. Bind board, role, method, request/version, native Doc when known, task and stable consumer execution; list applied entry IDs/versions/commit IDs and reasons, excluded entries/reasons, and complete assessment/Log observation references. The optional adapters return a selection for these records, not permission to bypass the normal role's preflight.

Executor uses the selected rules during drafting. Enforcer independently assesses the draft and originals against them; it does not accept the drafter's rationale as evidence. Feedback checks applicable decisions/rules before interpreting a human post and planning its authorized change. A confirmed rule does not expand any role's edit/reply rights.

## Before publication

Re-read relevant decision/rule state, confirmation, evidence and current Log entries. Compare the newly selected IDs/versions/commit IDs and scope against the saved companion, using actual current semantic assessment. Relevant changes stop for reconciliation; unrelated new entries do not force another review. Save the comparison evidence with the role's intent. Continue the registered same Doc; no automatic regeneration or second draft.

Executor method 1.4 retains the exact `executor-drafting/1` checkpoint and its builder's instruction revision 1.3. Save Judgment context as a separate companion, not extra keys in that fixed fourteen-field request/checkpoint. The companion and current authorization bind the new method. Installing a skill changes neither board configuration nor historical provenance.

## Automatic learning during this run

After assessing a new authorized item, consider a single useful reusable lesson. Use the Judgment workflow reference for duplicate checks, narrow scope, evidence, saved proposal intent and Log verification. Confirm the parent's explicit learning grant and authorized designated writer before any learning append; the old direct-edit/review grant alone is insufficient. The parent workflow and proposal have separate phases and identities. Complete the parent result even if the lesson remains unconfirmed; if learning fails after the primary effect, preserve both states and stop further dependent effects. Never reopen a completed parent to force a proposal.

Missing business facts are questions, not lessons. Repeated machine findings remain proposals, not confirmed preferences. Save `no_proposal` and the reason in the parent's normal result when no useful lesson is supported; avoid a separate audit append solely to say nothing happened.

Ordinary supported wording/formatting/clarification usually requires no Enforcer pass. Commitments, scope, safety, disclosures, previous findings or substantial uncertainty require a recorded review decision bound to the revised state. Feedback does not launch Enforcer; Judgment does not resolve ingestion Reviews, approve the Doc or complete business work.
