# Feedback Lab

## Revise a draft from a human comment

Continue work in your existing Google Doc. A human comments on a passage; Feedback makes the supported change directly in that Doc and replies in the original comment thread to explain what changed. Google Sheets remembers the request and result so a later run can recognize work already done.

This first lab uses one human comment, one small edit and one designated writer. Learning from feedback and completing the business task are separate features.

## Requirements and finish line

- Use your existing Hive Mind Sheet, accepted sources and registered draft. Preserve Tasks A–P, Reviews, Drafts and earlier records.
- Make a direct edit in the same native Doc. Do not create a replacement draft.
- Act only on an authorized human comment and facts supported by accepted sources.
- Reply once in the original thread, explaining the actual change. Leave the thread open for the human.
- Preserve formatting, links, other comments, protected passages and previous Executor/Enforcer work.
- Save the request, comment identity, intended change, actual edit, reply ID and final result in Sheets.
- Recognize an unchanged completed comment without making another edit or reply.
- Stop clearly if facts, permission, the target passage or the outcome of an earlier write are uncertain.

The finish line is one supported change, one matching threaded reply and a saved result. It does not mean the business task is complete.

## 1. Choose a safe starting point

Use your existing board. Identify the draft by its actual Doc link and saved task/Executor identity, rather than its title alone. Check for earlier Feedback work before requesting another change.

For the first exercise, use an authorized disposable test Doc registered on that same board. Keep historical drafts and completed tests unchanged. Do not reuse a completed test comment as new work. If a new fixture is needed, ask for a separately authorized test Doc in your approved Feedback folder; creating that fixture is setup, not a replacement draft produced by Feedback.

Choose a short plain paragraph with no pending suggestions or complicated structures. The current method supports one small inline change within one inspectable passage. It leaves documents with pending suggestions unchanged. It may also stop if another comment's location cannot be checked safely.

Keep Executor, Enforcer and other writers idle while Feedback works. This arrangement reduces conflicts; it is not a software lock. Avoid editing the Doc during the run.

## 2. Check the method and prepare the request

Use the installed Feedback skill if your class workspace provides it. The reference method is `hive-mind-feedback` version 1.0. Installation alone does not prove your Google account can read the board, edit this Doc or reply in this thread. The exercise checks those actions in your intended account.

If you are building your own method, start with these requirements and ask for a concrete plan before implementation. No code packet is required. You can use this brief:

> Build a manually started Feedback role for my existing Hive Mind board. A human comments on a registered draft; make only authorized, source-supported direct edits in that same native Doc, then reply once in the original thread explaining the change. Preserve human work, formatting, links, other threads, pending suggestions and Executor/Enforcer history. Use connected Google tools and Sheets for persistent memory. Save intent before edits or replies, retain returned IDs and reconstruct unfinished work without repeating effects. Keep task completion, learning and scheduling separate. Begin with one small inline change and one writer. Inspect current tools and records, identify concrete capability gaps, and present the plan before implementation.

For an installed method, use this setup prompt after filling in the links:

> Use the installed Hive Mind Feedback skill. Inspect my existing board [BOARD LINK], disposable draft [DOC LINK], accepted sources and saved registration. Prepare a proposed Feedback request for one small supported change. Report any missing registration, source acceptance, human-author confirmation or connection capability. Show exactly which setup records you would append and which Doc/thread the request would authorize. Preserve historical records, Tasks A–P, Reviews and Drafts. Do not write or run the request yet.

Review that proposal. Confirm the exact Doc, sources, permitted commenter and single writer. Then explicitly authorize the bounded setup records and request. Registration must retain the draft's original task and Executor identity; a disposable fixture must be labeled as a test. A new request name cannot make an already handled comment eligible again.

## 3. Add and authorize one human comment

In the test Doc, select a sentence and add a comment asking for a small change already supported by an accepted source. For example, if the accepted scope says the total session is 20 minutes including questions, select “Duration: 20 minutes.” and comment:

> Please clarify that the 20 minutes include questions.

Use that example only when your accepted source actually supports it. Do not introduce new business facts just to make the test work.

Tell Work you personally added the comment, giving the Doc link and exact wording. Ask it to identify the original thread and bind that post to the request. Confirm permission to edit that specific passage and reply in that thread. A display name or “same account” indicator alone does not prove a human wrote a comment; automation can use the same account.

If the request was prepared before the comment existed, authorize its final binding and enablement now. Keep that authorization in the board's durable records, rather than relying on this chat alone.

## 4. Run the edit and reply together

Use the registered request ID and version from setup:

> Use the installed Hive Mind Feedback skill. Board: [BOARD LINK]. Request: [REQUEST ID], version [VERSION]. Reconstruct the enabled request, human authorization, registered Doc, accepted sources and any previous effects from durable records. Complete this authorized item in one run: make the smallest supported direct edit in the same Doc, verify it, reply exactly once in the original human comment thread explaining the actual change, then save and read back the final result. Preserve formatting, links, protected content, other threads and original provenance. Leave the thread open. Do not create another draft, run Enforcer, change task status, activate lessons or schedule anything. Do not pause deliberately between the edit and reply. If a required check fails or a write outcome is uncertain, stop and report the exact issue and known IDs. If already complete and unchanged, return the saved result without writes.

You do not need to interrupt the run deliberately or repeat the project's recovery test suite for this lab.

## 5. Inspect the result

Open the same Doc and original comment thread. Check that:

- The requested sentence changed accurately and still matches the accepted source.
- Exactly one reply explains that change in the original thread, which remains open.
- Formatting, links, protected text and other comments remain intact.
- Work reports the saved outcome and same Doc/thread/reply identities, or clearly explains why it stopped.

For the example above, the sentence should read “Duration: 20 minutes, including questions.” The total remains 20 minutes.

To check that a later conversation recognizes completed work, start a fresh conversation with the installed skill and use this read-only prompt:

> Board: [BOARD LINK]. Feedback request: [REQUEST ID], version [VERSION]. Reconstruct the result from durable instructions and records. Inspect the current Doc and original thread. Return the saved change, reply identity, original completion time and next permitted action. Do not edit, reply, append records or run the workflow.

An unchanged completed item should permit no additional edits or replies. A new or edited human request needs its own linked feedback item/version and authorization.

## When the comment needs a decision

Questions may receive a source-supported answer. Missing facts or an unclear target require clarification before editing. Conflicting comments require a human decision. An acknowledgment usually needs no reply.

Ordinary wording, formatting and supported clarifications normally need no new Enforcer review. Changes involving commitments, scope, safety, disclosures, a previous Enforcer finding or substantial uncertainty need a recorded review decision. Feedback does not launch Enforcer automatically or replace its earlier report.

“Looks good,” resolving a comment and accepting a suggestion do not complete the business task. This lab changes no task status and proposes or activates no reusable rules.

If the run stops after an edit or reply, keep the same request and saved IDs. Ask it to inspect the saved and current state before continuing. Do not create a new request or repost the comment to force another attempt.
